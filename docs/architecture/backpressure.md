# 积压容量与异常恢复

2026-10-24，v0.4 第一阶段实现补充。目标是接收速度长期高于发送速度、目标不可用或单条数据过大时，有界接收并保留已经承诺接收的工作。P0 已补静态多目标调度和授权恢复，见[P0 实现](p0-operations.md)；P1 已补内容引用、独立文件配额与流式 HTTP，见[P1 实现](p1-storage.md)。

## 容量口径和默认值

| 配置 | 默认值 | 语义 |
|---|---|---|
| max_pending_items | 10000 | 每工作区未完成的逻辑工作数；一个入站事件或一个非空回复命令占一项 |
| max_pending_bytes | 268435456 | 256 MiB 逻辑积压正文预算；事件按持久化信封编码大小，回复按各目标投递记录大小总和计费 |
| resume_percent | 80 | 暂停后，条数和逻辑字节都降至上限的 80% 以下或相等，才可恢复 |
| min_free_disk_bytes | 268435456 | 数据库所在文件系统可用空间低于 256 MiB 时拒绝新的工作 |
| resume_free_disk_bytes | 536870912 | 已暂停时，可用空间达到 512 MiB 且逻辑积压达到低水位，才可恢复 |

配置保存在 SQLite，所有连接读取同一份策略。Pipeline 启动时将操作者配置写入策略；普通 SqliteStore::open 不覆盖已有策略。现阶段每份数据库只运行一条静态 Pipeline，不能用不同配置的多个实例争抢策略。旧配置省略 capacity 时采用上述默认值。

逻辑字节不是数据库文件或 RSS 的硬上限。自动路由的目标正文副本、索引、审计、历史记录和 WAL 不重复计入该事件的逻辑额度；静态链路已可配置最多 32 个目标。存储端额外限制单事件/单投递编码为 256 KiB、每批最多 32 个目标，回复幂等指纹也最多 256 KiB。多目标按放大系数预留物理预算仍需后续实现，不能从逻辑额度推断实际占盘上限。

文件系统空间检查是接纳时的保护，不是操作系统级磁盘预留；其他进程仍可能耗尽空间。探测失败拒绝新工作。当前使用 Unix statvfs，已在 macOS 验证；其他平台需提供空间探测实现，不能静默跳过。

## 接收和释放

接收事务先检查来源去重，再校验编码大小、容量与磁盘水位，原子写入 pending_work、Event 和 RoutingTask。触发高水位时提交暂停标记，但不保存被拒绝的事件。多个连接并发接收仍由同一事务与计数约束裁决，不存在先查余量再独立写入的竞争窗口。

同一来源 ID 的重复提交返回原 event_id，不重新计费；已经入库的重复事件在磁盘低水位或逻辑满载时仍可查询确认，但底层数据库本身不可读或在途接纳满载时仍可能返回暂时失败。相同 ID 携带不同内容沿用现有契约，不覆盖原消息。

事件进入路由和 Outbox 后，原额度继续保留，避免把接收积压转移到投递表后看似消失。全部目标状态为 submitted（渠道确认接收）或经授权明确终结后才释放；人工重放的新任务完成前仍保留额度；空计划直接释放。完成状态与额度释放在同一事务中，重复/旧租约不能重复释放。

failed、reconcile、blocked 继续占用额度并保留内容。P0 已增加独立权限的核查/放弃/重放命令；状态未明确终结前仍占用额度，不会自动删除，也不提供任意 SQL 重置。逻辑额度释放不删除历史正文，因此历史文件仍会增长；清理保留策略另行实现。暂停标记在下一次新工作接纳时重评估，读状态时可能仍显示刚排空后的旧暂停状态。

HTTP 容量不足返回 503 capacity_exceeded 与 Retry-After: 10；未确认接收的调用方使用原 source_event_id 重试。编码后单事件过大返回 413，不能通过无限重试解决。原有 HTTP 原始正文 64 KiB 上限继续有效；内部 SDK/来源构造的事件也经过存储编码限额。

## 失败任务隔离

新增 routing_tasks：ready、retry_wait、blocked、completed，包含失败次数、到期时间和安全错误分类。扫描只选择已到期 ready/retry_wait；已被阻塞的旧任务不会反复占据前 100 条窗口。路由成功的 dispatch 标记、投递记录与 completed 状态在同一事务提交。

暂时不可用、限流、容量不足、超时、状态冲突和结果未知采用有上限的退避；累计第 8 次失败转 blocked。永久输入/权限/适配器错误直接 blocked；取消不增加失败次数。重启保留状态与到期时间，晚到的失败报告不能把 completed 改回失败。这个表目前是单实例调度状态，尚未提供分布式路由领取租约。

路由重试只重新规划并幂等提交，不重跑已完成的投递。当前通用 HTTP 目标仍为 NonIdempotent，网络结果未知或服务器错误进入 reconcile，不能因增加背压机制就启用盲目发送重试。

## 为完成操作保留容量

SQLite 保留普通操作 64 个在途名额，另设 8 个关键操作名额，供发送状态、完成记录、结束审计、路由失败保存及容量配置使用。大量接收不再耗尽关键操作的接纳名额。二者仍共享一个连接和 5 秒异步等待上限；这不是抢占式数据库调度，不能保证数据库被外部进程锁住时关键操作及时成功。

SQL 已开始时，调用方取消仍由阻塞闭包持有连接和容量直到结束。状态提交失败继续保留结果未知语义，不能为了释放额度伪造完成。

## 数据库升级和检查

本阶段最初将 schema 从 v1 升至 v2；P0 进一步升至 v3，原有事件、投递、审计正文编码保持兼容。版本变更、表/索引和回填在同一事务：为旧事件补路由状态，为未完成事件和回复补额度；已完成 dispatch 不再路由，submitted 不变成 pending。旧库若已超过默认限额，新接收会暂停，原工作不会被丢弃。升级失败事务回滚；升级成功后旧版程序不支持 v2，回退须恢复升级前的一致性备份并核查外部发送。

本次仅用测试临时库验证迁移，没有打开或升级用户部署库。实际升级前停止服务并准备一致性备份。

只读检查命令不读取消息正文或秘密：

```sh
python3 scripts/inspect_backlog.py data/synquay.db
python3 scripts/inspect_backlog.py data/synquay.db --workspace 00000000-0000-0000-0000-000000000001
```

输出逻辑容量、文件系统可用空间、最老积压年龄、路由/投递各状态数量。它不修改暂停标记、不触发重试、不删除数据。

## 验收和后续

覆盖多连接竞争额度、重复确认、高低水位恢复、全部目标完成释放、磁盘不足模拟、大记录拒绝、失败任务隔离、旧库回填与失败迁移回滚、关键名额保留，以及真实 HTTP 目标失败后重启不重复发送。磁盘不足通过提高配置阈值模拟，未填满真实磁盘或注入真实 I/O 故障。

目标级限速/熔断已在 P0 实现；P1 已补大内容引用、流式传输及正文/幂等分离保留；后续继续有效期/状态合并等显式业务策略，以及容量压测与 RSS/尾延迟测量。持续超载只能通过提高处理能力、上游限流或显式业务降级收敛，不能靠无限扩大队列解决。
