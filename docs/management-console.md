# 管理台运行与验收

2026-10-25。管理台提供“开始使用、连接、Agent 接入”，支持在线新增 HTTP 能力、保存恢复、能力发布、接入信息与服务内实际调用验证。沿用 React + Vite，以用户接入顺序组织入口。

## 本地启动

先按 [MCP 工具说明](architecture/mcp-tools.md) 准备可信工具配置。`examples/tools.json` 中的 echo 上游仅是演示配置，需要真实调用时另行启动对应服务。管理台不会自动调用工具。

管理台目前不要求登录或管理员令牌；MCP 客户端仍需独立认证。使用静态 MCP 模式时，准备至少 32 位的随机令牌并安全注入 `SYNQUAY_MCP_TOKEN`；OAuth 模式使用现有授权配置。随后从仓库根目录运行后端：

```sh
export SYNQUAY_TOOLS_CONFIG=examples/tools.json
export SYNQUAY_TOOLS_SECURITY_CONFIG=examples/tools-admin.example.json
cargo run --locked -p synquay-server
```

另一个终端运行前端：

```sh
npm run dev:frontend
```

访问 `http://127.0.0.1:5173/` 会直接进入管理台并自动读取当前空间。已删除登录页、“服务连接”页面、手动令牌输入与断开连接入口。读取失败时显示真实错误和重试按钮，不创建演示数据。

后端默认地址为 `http://127.0.0.1:8080`；不同地址可通过 `SYNQUAY_API_TARGET` 指定开发代理目标。代理转发 `/api`、`/mcp` 和 `/.well-known`。管理接口不再校验 Authorization，也不读取管理员令牌环境变量。此阶段没有管理台用户身份认证；完整认证体系后续实现。

同源浏览器请求可直接访问管理接口。额外开发来源仍可在 `admin.allowed_origins` 中精确配置；重复 Origin、跨站 Fetch Metadata 和未允许的来源被拒绝，不开启宽松 CORS。`admin.principal_id` 仅保留操作审计和恢复作用域，未配置时使用原工作空间 bootstrap 主体；它不代表已认证用户。旧 `admin.token_env` 配置只兼容读取、不使用、不序列化。MCP OAuth/Bearer、工具执行授权、webhook 验签及独立运维接口的认证不在本次移除范围内。


## 编辑与恢复

勾选能力只改变页面编辑状态。保存草稿使用草稿代数和发布基准版本进行 CAS；预览显示新增、移除及不变能力，确认后才发布。工具的副作用标记来自可信配置，未知不当作只读；工具详情中的凭据只显示引用名称。

发布前把 operation_id、expected_revision、draft_generation 写入当前标签页的 sessionStorage，用服务及管理员标识隔离；这里不存令牌或能力参数。若会话存储不可用则不发起发布。刷新或重新认证后保留原发布意图，需主动查询结果或使用原编号重试，不自动提交。

`unconfirmed` 仅表示尚未查询到已提交回执，操作可能仍在运行，不代表失败。已提交回执具有权威性，即使随后读取配置失败也会保留成功结果。版本冲突会停止发布并提示读取最新版本；重新读取可保留本地选择，但需重新检查和保存。

前端不保存或发送管理凭据。已接纳的发布仍在后台完成；页面刷新后按既有操作编号核查。工作空间停用约束、成员边界、版本冲突、幂等与审计继续保留。

## API 与存储

管理台 `/api/tools/*` 与 `/api/workspace*` 接口暂不要求登录，并返回 `Cache-Control: no-store` 与服务端生成的 `x-request-id`。错误使用安全 `code`；界面不会展示上游错误正文。新的查询端点：

| API | 语义 |
|---|---|
| GET /api/tools/history?limit=10&before_revision=2 | 版本倒序游标分页；limit 为 1–50；返回版本、时间、操作者、开放能力和下一游标 |
| GET /api/tools/operations/{id}?expected_revision=1&draft_generation=1 | 只读核查原操作，返回 committed + receipt 或 unconfirmed；同编号不同参数返回冲突 |

`GET /api/tools/config` 增加 admin_id 和 connection 元数据。OAuth 地址来自可信配置；静态 Bearer 模式的 UI 地址按当前同源地址推导，部署时须配置对应代理。

历史查询自 SQLite v7 起增加 `tool_publications(workspace,profile,revision)` 唯一索引。历史查询从 `tool_releases` 复合主键进行范围扫描，再按新索引关联审计；操作核查复用原操作表复合主键。每页最多读取 limit+1 行，没有全表排序或 offset 扫描。历史响应不包含完整连接快照或秘密引用。

### 在线新增 HTTP 能力

连接 → 添加连接 → HTTP 地址 → 能力名称、用途/调用条件、操作性质、输入 JSON Schema → 检查并保存。

- 当前每项能力独立绑定一个无认证的 JSON POST 端点，总计最多 32 项。不是通用 HTTP 请求编辑器，尚不支持任意请求头、GET、OpenAPI 导入或连接的一对多能力编辑。
- URL 不接受 userinfo、查询与 fragment；默认 HTTPS，本机 HTTP 需显式允许。JSON Schema 在后端编译、校验；未知副作用不当作只读。
- 新项固定为未开放，保存不调用上游。保存增加 Profile revision，原开放能力保持不变，旧目录客户端应重新读取版本。既有草稿不会自动合并或发布。
- 下一步在 Agent 接入勾选能力、保存草稿、预览并发布。OAuth 的逐工具 grants 不会自动扩大，仍需管理员在服务端配置授权并重启；静态调用令牌沿用已有工作区/能力授权模型。
- 带凭据的工具仍使用启动配置和环境秘密引用。MQTT、CLI、上游 MCP 目前只有抽象，不在 UI 提供假成功配置。
- 新增记录持久化到数据库，启动时与文件配置合并；不要再把同一条在线连接复制到启动文件。当前在线修改、删除连接尚未提供。

新增 API：

| API | 语义 |
|---|---|
| POST /api/tools/connections | operation_id = 新 connection_id，expected_revision CAS；提交隐藏能力 |
| GET /api/tools/connections/{operation_id} | 同管理员、同空间/Profile 的创建回执核查 |
| POST /api/tools/verify | 携带单独 MCP 调用令牌，execute 或 inspect；只返回状态和调用编号 |

三个接口均处于管理员认证、精确 Origin 校验、并发上限之内。POST 限制为 JSON、32 KiB、5 秒读入超时。数据库 v9 的 managed_tool_connections 复合主键支持回执查询，唯一索引 (workspace, profile, revision) 支持按版本恢复。连接、版本头、快照和发布审计同事务提交，审计写入失败整体回滚。

内存注册表、Schema 缓存和只读能力集合支持有界的增量注册，共享 HTTP client 与执行并发额度；不会为新连接另开线程池或客户端池。新增操作与发布共用互斥和发布读写门，已接纳调用结束后再激活。提交之后若运行时激活异常，返回结果未知；查询 committed 只证明持久化提交，应重启服务重新加载并检查调用，不能视为连通性证明。

### 实际调用与不确定结果

Agent 接入 → 接入方式 → 验证一次服务内调用。输入 MCP 令牌、已发布能力和参数，检查操作影响后主动执行。管理台不再要求登录，但 MCP 调用仍独立认证；正常的 Profile、空间成员、OAuth grants、输入校验、执行额度、持久调用账本与审计链路都会生效。验证不返回上游正文，也不证明外部 AI 客户端已经连接。

浏览器仅存恢复编号，令牌与参数仅驻留页面内存。新建连接保存结果不明时暂停创建、允许原编号重试；重新加载后仅能查询。调用结果不明时仅查询原调用，绝不自动重发。参数/认证等明确拒绝后可改正重试。必要时管理员可确认已在服务端/目标服务核查，再结束本地跟踪；该操作不会取消任何后台任务。

本次浏览器验收使用独立的 `data/console-onboarding` 数据库：前端 5174、后端 8082、本地 echo 8093。空空间开始，经创建隐藏能力 v2、发布 v3、执行 echo 到成功状态。原 5173/8080 预览没有替换；若查看新版，请访问 5174。此预览只供本机开发，尚未部署公网。

## MCP 多服务管理（2026-10-25）

顶部次序为 MCP 服务、连接，默认进入服务列表。支持创建、编辑名称与工具范围、启停和删除；服务管理 API 为 `/api/tools/servers` 与 `/api/tools/servers/{id}`。创建和更新使用 PUT、客户端固定 UUID、操作 UUID 和版本 CAS；删除使用 DELETE 加操作 UUID 和预期版本。超时不自动创建新服务，界面提供原操作重试。

原 `/mcp` 服务自动登记为默认服务。新建服务默认生成 `/mcp/` 加 8 位随机字符的地址，允许编辑完整公开 URL（路径 `/mcp` 或 `/mcp/{名称}`）。工具目录和发布版本独立，共用可信连接注册表和执行预算。每个服务独立管理工具、资源（含资源模板）和提示词的开放范围；Agent 任务仍仅由默认服务提供。各服务可独立选择 Basic Auth、JWT（RS256）、OAuth 或无鉴权；旧服务保留原部署认证，编辑器不提供新增“沿用部署认证”选项。

SQLite v12 增加服务记录与变更审计，v13 增加路由路径及工作空间内活动路径唯一索引。按工作空间查询、服务 ID 查找和活动服务名称去重建索引。服务修改与 Profile 发布同事务提交，使用既有发布锁等待已接纳调用完成；停用/删除阻止后续访问。删除保留历史和墓碑，重启不恢复旧端点。当前每空间最多保留 64 条服务记录（包含已删除记录）；达到限制返回容量错误，后续需补历史保留策略。备份和检查脚本支持 v13。

### MCP 服务卡片与编辑

卡片分两行：首行是名称、地址和客户端数量位置；第二行是用户填写的用途说明与工具名称，以及非零的资源/提示词数量。右侧仅启用/停止、编辑、删除三个图标操作。复制成功时图标暂时变为勾，不显示全局提示。当前无状态 HTTP 不保留客户端会话，按用户要求显示“客户端 0”；它不是近期调用者统计。

编辑窗口的标签和输入同行排列，显示名称、说明、可修改地址、传输方式、认证字段及开放能力。没有启用开关、独立接入面板和说明性段落。工具详情只显示名称、参数和说明。

服务保存保留版本 CAS、幂等操作编号及未知结果恢复。地址改变会更新实际路由，旧路径停止接收请求；同一工作空间不能重复占用路径。公开 URL 的主机与 HTTPS 入口仍由部署和反向代理提供，修改地址不会创建 DNS 或证书。允许 HTTPS，本机可使用 HTTP；不接受查询参数、片段或 URL 用户名密码。

逐服务认证支持 Basic Auth（密码环境变量引用）、JWT（固定 RSA 公钥、RS256、Issuer/Audience/Subject 和有效期验证）、OAuth（外部授权服务 introspection、Scope 和调用主体限制）及无鉴权。密码和客户端密钥不存入数据库，只保存环境变量名，保存时验证引用。OAuth 的资源地址与公开 MCP 地址保持一致；仍使用部署 OAuth 的旧服务需要显式切换独立 OAuth 配置后更改资源地址。鉴权结果绑定服务与版本，不能用于其他服务。

目前传输方式仅实现无状态 Streamable HTTP；编辑器不提供未实现的传输选项。

### 按服务管理资源与提示词

编辑区使用“工具 / 资源 / 提示词”三个标签页，资源模板归入资源并标注“模板”。卡片直接显示前三个工具名称，超出部分显示剩余数量；资源、提示词为零或未知时不显示。点击对应内容查看名称、说明及参数。管理接口仅返回内容目录元数据，不返回资源正文或提示词消息正文。

服务记录的 `content_scope` 保存资源 ID（包括模板）与提示词 ID，和工具发布、服务版本及审计同事务提交。更新带 `expected_content_revision` 校验所见目录版本，防止旧目录误授权；重复或未知 ID 拒绝。旧客户端省略范围时保留原设置；新服务默认不开任何资源和提示词。旧默认服务缺少该字段时兼容启动配置的 exposed 标记。

每个请求使用共享内容提供器构建该服务的作用域视图，不复制资源正文。资源 URI 包含实际服务 ID 与目录版本，读取、提示词获取和参数补全都校验当前持久化范围、调用身份、空间权限以及适用的 OAuth grant。停用、删除、配置撤销后旧身份不可继续读取。订阅和流式事件尚未在本次实现中开放。

范围随既有服务 JSON 记录保存，通过已有工作空间/服务 ID 主键读取，不增加无用途的数据库索引。源内容仍由可信部署配置提供，本次管理台负责选择开放范围，不提供内容正文编辑。

### 路由管理（第一阶段，2026-10-25）

顶部导航新增“路由”。默认路径卡片展示名称、启停状态、`Webhook → 直接转发 → HTTP 目标`，右侧提供启停、编辑和删除。多目标纵向分支排列，前三项之外折叠为数量；关系图按来源、路由、目标自动排布，点击路由可编辑。编辑分为来源、处理、目标，支持精确事件类型过滤、目标多选和路径预览。新建路由默认停止。

真实运行范围：最多 16 个部署配置的 Webhook 来源、最多 32 个已配置 HTTP 发送目标。端点来自 `SYNQUAY_PIPELINE_CONFIG`（示例 `examples/pipeline.multi-target.example.json`），管理台 MCP runtime 与 pipeline 必须属于同一空间。`scripts/restart_console.py` 优先读取显式 `SYNQUAY_PIPELINE_CONFIG`，否则自动加载 `data/console-onboarding/pipeline.json`；文件存在时校验与管理台空间一致，并从环境或本地 `webhook-token` 加载入口密钥。缺少配置才显示未配置提示。当前 HTTP 工具连接不是 pipeline 发送端，尚不支持把连接页新建的工具直接选作目标。

接口：GET `/api/routes` 返回能力可用性、端点、快照和投递计数；POST 同地址接收 `operation_id`、`expected_revision`、`route_id`、`change`（save/delete）；GET `/api/routes/operations/{operation_id}` 仅查询原操作结果。使用既有同源校验、空间管理员权限及活跃空间检查，当前仍沿用管理台开发期无登录模式。保存使用 CAS 与不可变回执；前端仅在结果不确定时保留同一请求用于查询/重试，不自动重新提交。临时恢复信息按空间与管理身份隔离，不含认证凭据。

SQLite v15 以部署主来源为键保存有界路由聚合快照和操作审计，作用域复合主键支持直接定位；空快照防止删除后重启重新生成默认路由。投递表增加规则 ID，使用 `(workspace, route_rule_id, state)` 部分索引统计当前目标保留期内的记录，不扫描 JSON 负载。最多 64 条路由，所有启用规则合计最多 32 个分支，与 outbox 一次原子分发上限一致。多个命中规则可以分别投递到同一个目标，配置者应使用过滤避免不需要的重复发送。

保存与当前分发批次串行衔接；断开的 HTTP 请求不会中断已开始的提交与内存激活。停止/删除不撤回已经排队的投递，恢复启用不重放已处理的事件。匹配发生在分发时，尚未处理的积压事件使用当时生效的规则。现有已分发消息保留原规则版本；修改目标不会改写历史。计数在进入页面、刷新或保存后更新：“已提交”是 HTTP 目标接受，不代表设备执行；“需处理”汇总失败和不确定结果，不触发自动重试。

### 多入口与 Agent 流程预览（2026-10-25）
